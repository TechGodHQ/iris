# Design: Realtime Subscriptions

## Core contract

`MessageProvider` gains `async fn subscribe_realtime(&self) -> Result<BoxStream<'static, Result<Message>>>` plus an idempotent `async fn shutdown_realtime(&self) -> Result<()>` whose default is a no-op. The outer result rejects an unsupported or currently unavailable subscription; stream items carry runtime failures. A provider that does not advertise `ReceiveRealtime` uses the default `UnsupportedCapability` implementation. `iris-core` owns the `BoxStream`/item contract and lifecycle hook only and remains free of provider/network I/O. Server application shutdown owns calling and awaiting `shutdown_realtime()` for every instantiated provider.

A stream error is terminal for that subscriber unless explicitly marked recoverable by a future typed event contract; this change has no recoverable error events. Static `ReceiveRealtime` means a provider can implement the feature; runtime readiness additionally requires enabled configuration and an audit sink. `subscribe_realtime()` returns `RealtimeUnavailable { code }` when that readiness check fails. Realtime audit uses a versioned, fixed content-free metadata schema: `schema_version: 1`, `event_kind` (`message`, `ignored_update`, or `invalid_update`), `provider`, `update_id`, nullable `source_id`, `thread_id`, `message_id`, `message_kind`, `timestamp`, and attachment `{mime_type,name,byte_count}` summaries. No body, credentials, token, raw payload, URL query, or raw bytes may be recorded.

## Telegram polling and delivery

One provider instance owns one process-memory poller and cursor; restarting Iris starts with Telegram's normal backlog because persistent cursor storage is out of scope. The poller calls `getUpdates` with `timeout=30`. It has a cancellation token owned by a `RealtimeHub` held by the provider; cancellation aborts an in-flight request, joins the task, and happens on application shutdown or after the last subscription drops.

The hub maintains a registry of bounded per-subscriber queues with 128 message slots plus an out-of-band terminal state. A `subscribe_realtime` call registers one receiver, starts the poller if absent, and returns that receiver's fallible stream. Each subscriber sees Telegram updates in poll order from the point it joins. A full message queue atomically records `SlowConsumer` in its terminal state and is removed; the stream SHALL yield that error before ending, without blocking or disconnecting other subscribers. The poller stops when the registry becomes empty. A later subscription starts a fresh poller using the process-memory cursor and receives only events accepted after it joined.

For a Telegram update containing a normalizable message, the hub snapshots its subscriber registry before normalization. The commit point is: normalize (including existing eager attachment persistence), validate the fixed audit metadata, atomically `record_once(("telegram", update_id), event)`, then attempt enqueue to that snapshot. `record_once` returns `Inserted` or `AlreadyRecorded`; it enforces uniqueness inside the audit backend under its existing cross-process lock, and `AlreadyRecorded` proceeds to fan-out without a second audit record. The offset advances to `update_id + 1` after the audit operation succeeds and either a snapshot subscriber accepts, every snapshot subscriber is terminally removed for overflow, or every snapshot subscriber has naturally disconnected. Thus an audited update is never replayed merely because clients disconnected during dispatch. This is best-effort live delivery, not durable replay; healthy subscribers preserve order.

The poller requests all Telegram update types (it SHALL NOT use an `allowed_updates` filter), retains `update_id` before decoding an update body, and treats no-message/unsupported shapes as `ignored_update` and decode/normalization failures with a known ID as `invalid_update`; both are `record_once` diagnosed and acknowledged. A whole response that cannot expose an update ID is a transient protocol error. Attachment storage failure and audit write failure are terminal to all current subscribers, stop the poller without advancing that update, and leave retry to a later subscription/process restart. Telegram HTTP 409 is likewise terminal to every subscriber, stops without retrying, and does not advance. Transport, response decode, HTTP 429, and HTTP 5xx retry up to `realtime_retry_budget` (default 3, minimum 1) after 250ms, 500ms, and then capped 1s exponential delays without jitter; other 4xx errors are terminal. After exhaustion the hub emits `RealtimeRetryExhausted`; all numeric settings are constructor-validated.

## SSE surface

`GET /v1/events` is an SSE-only route with `Content-Type: text/event-stream; charset=utf-8` and `Cache-Control: no-cache`. It is not a unary generated route. `provider` and `thread_id` are optional exact-match filters. A selected provider that is unknown, disabled, does not advertise realtime, or fails runtime readiness returns HTTP 422 JSON `{ "error": "unsupported_realtime_provider", "provider": "..." }`. For an unfiltered request, the server attempts each enabled capability-positive provider: unavailable providers are omitted, but if none subscribe successfully it returns HTTP 503 JSON `{ "error": "no_realtime_provider" }`.

A message is `event: message` with JSON `Message` data. A terminal provider item is `event: error` with `{ "provider": string, "code": string, "message": string }`. Public codes are exactly `slow_consumer` (queue overflow), `telegram_conflict` (HTTP 409), `audit_failed` (audit/storage failure), `retry_exhausted` (transport/429/5xx budget exhausted), and `provider_failed` (other terminal provider/4xx failure); `message` is sanitized of credentials and upstream URL details. An unfiltered aggregate keeps other provider branches alive, then emits its final error and closes when its last branch terminates; a provider-filtered stream closes after its error. The server emits an SSE comment heartbeat at least every 15 seconds of wire-idle time; filtered-out events do not reset the heartbeat. Dropping the HTTP connection drops its provider subscriptions and releases hub capacity.

## Generated API and CLI contract

Extend `api/operations.yaml` and `iris-codegen` with `delivery: sse` and explicit `surfaces: [http, cli]`. The exact `subscribe_events` operation is `method: GET`, `path: /v1/events`, query parameters `provider` and `thread_id`, and `delivery: sse`. Generator validation SHALL reject `delivery: sse` unless `http` is present, SHALL exclude it from MCP and unary handler generation, and SHALL emit only route/CLI metadata plus a named runtime binding hook. The handwritten server binds that hook to the sole `/v1/events` handler, so no duplicate Axum route exists. The generated CLI artifact declares `iris watch` and endpoint/filter options. Runtime wiring supplies its behavior: `IRIS_SERVER_URL` (default `http://127.0.0.1:3000`) plus `--provider` and `--thread-id`; it parses SSE frames, writes every `message` JSON unchanged as one stdout line, writes `error` diagnostics to stderr, and exits non-zero when its selected stream or all aggregate branches terminate in error.

## Testing and constraints

Use mocked Telegram responses and deterministic paused time. Cover unsupported defaults; multiple subscribers/no competing pollers; per-subscriber order; overflow and unaffected healthy subscribers; last-disconnect and shutdown cancellation during long poll; offset and poison-update policy; audit idempotency/failure; 409 and retry-budget behavior; SSE statuses, schemas, filters, heartbeats, disconnect cleanup; CLI stdout/stderr and aggregate versus filtered error exits; and codegen freshness. The frozen proposal must not change during implementation; deviations go in `RUNNER.md`.
